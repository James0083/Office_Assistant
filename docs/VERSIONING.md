# 버전 관리 가이드

## 버전 번호 규칙 — `주.부.수` (예: 1.2.3)

| 자리 | 언제 올리나 | 예 |
|---|---|---|
| **수** (PATCH) | 버그 수정, 문구·디자인 수정. 데이터 형식 그대로 | 저장 충돌 오류 수정 → 1.0.0 → **1.0.1** |
| **부** (MINOR) | 새 기능 추가. 예전 버전 앱과 같은 `data.json` 을 같이 써도 문제없음 | 메뉴얼 탭 추가 → 1.0.1 → **1.1.0** |
| **주** (MAJOR) | 예전 버전 앱과 같은 `data.json` 을 같이 쓰면 안 되는 변경 | 관리자 잠금 추가 (예전 앱은 잠금을 무시함) → 1.1.0 → **2.0.0** |

- 앞자리를 올리면 뒷자리는 0 으로: 1.4.2 → 1.5.0, 1.5.0 → 2.0.0
- 한 번 배포한 번호는 다시 쓰지 않는다.

### '주' 를 올려야 하는지 판단하기

이 앱은 공유 폴더의 `data.json` 하나를 여러 컴퓨터가 함께 쓰므로, **한 대만 새 버전이고 나머지는 예전 버전**인 상황이 생긴다.
아래 중 하나라도 해당하면 **주** 버전이다.

- 예전 앱이 새 데이터를 읽지 못하거나 화면이 깨진다
- 예전 앱이 저장하면서 새 데이터를 지우거나 망가뜨린다
- 예전 앱이 새 규칙(예: 관리자 잠금)을 무시한다

이때는 **모든 컴퓨터의 앱을 한꺼번에 바꿔야** 한다고 공지한다.

> 참고: 지금의 `app.py` 는 저장할 때 모르는 항목(예: 새로 생긴 `manuals`)도 그대로 둔다.
> 그래서 새 종류의 데이터를 **추가**하는 것만으로는 예전 앱이 데이터를 지우지 않는다 → 보통 **부** 버전.

## 버전을 적는 곳

**[app.spec](../app.spec) 의 `VERSION` 한 곳만** 바꾼다. 빌드하면 아래에 자동으로 들어간다.

- macOS: Finder → 앱 선택 → 정보 가져오기
- Windows: exe 오른쪽 클릭 → 속성 → 자세히

## 배포 순서

1. 수정 작업을 마치고 커밋
2. [app.spec](../app.spec) 의 `VERSION` 을 올린다
3. [CHANGELOG.md](../CHANGELOG.md) 맨 위에 새 버전과 바뀐 내용을 적는다
4. 커밋하고 태그를 붙여 올린다
   ```sh
   git commit -am "버전 1.1.0"
   git tag v1.1.0
   git push origin main --tags
   ```
5. GitHub → Actions → 해당 실행 → Artifacts 에서 `macOS`, `Windows` 를 받는다
   (`Windows-screenshot` 으로 exe 가 정상 실행되는지 확인)
6. 공유 폴더의 앱을 교체한다. **주** 버전이면 모든 컴퓨터를 한꺼번에.

태그(`v1.1.0`)를 붙여 두면 나중에 "1.1.0 때 코드" 를 바로 찾을 수 있다: `git checkout v1.1.0`

## CHANGELOG 쓰는 법

사용하는 사람이 읽는다고 생각하고, 무엇이 달라졌는지만 짧게.

```markdown
## 1.1.0 — 2026-11-02
- 추가: 메뉴얼 탭
- 수정: 템플릿 변수를 바꾼 뒤 저장하면 충돌 경고가 뜨던 문제
```

`추가` / `변경` / `수정`(버그) / `삭제` 로 나눠 적는다.
